# Phase 2 invoice intelligence

This feature runs in `TRUSTPAY_BACKEND=postgres` with Supabase Auth, the private `invoice-documents` bucket, and migration `20261123000300_invoice_intake.sql`. SQLite remains the separate synthetic demo. The browser calls the Next.js server with the user's Supabase access token and selected organization. All intake queries scope by that organization. The server encrypts extracted fields, including the full IBAN, with the existing AES-GCM key and keeps documents in private Storage. API responses show the full proposed IBAN only to an authenticated organization member during review; persisted risk results show masked account identifiers.

## Configuration

Install `requirements.txt`, apply all Supabase migrations to an explicitly designated development project, and configure the existing PostgreSQL, Supabase, and IBAN key variables in `.env`. For **synthetic development invoices only**, set `OPENAI_API_KEY`, `TRUSTPAY_ENVIRONMENT=development`, and `TRUSTPAY_AI_EXTERNAL_DOCUMENTS=development` to enable the vision reader and AI evidence summary. `TRUSTPAY_AI_MODEL` defaults to `gpt-5.4-mini`, which [supports image input and structured outputs](https://developers.openai.com/api/docs/models/gpt-5.4-mini). The provider has a 30-second timeout, one retry, structured Pydantic output, and `store=False`. Keep the API key on the backend. With external processing disabled, text PDFs use the local pypdf reader; scanned PDFs and images enter an explicit provider-unavailable state and can be entered manually or retried later. Do not enable external processing for customer documents without authorization and data-processing controls.

## Workflow

An analyst, owner, or admin uploads a PDF, PNG, or JPEG of at most 10 MB. the Next.js server validates content signatures and decodes images with a 20-million-pixel cap, limits each uploader to 20 intakes per hour and each intake to two extraction retries, stores the original privately, and proposes fields. Conflicting or missing required fields are marked for review. The user corrects all fields and selects an existing supplier or confirms a new supplier. A reviewed invoice is passed to the existing deterministic TypeScript policy engine. Its immutable assessment and signals are stored in PostgreSQL. A separate optional model summary receives only the masked account identifiers, score, historical payment count, level, and signal codes; it cannot change the policy decision. If the model is unavailable, the policy explanation is saved instead. Existing verification, maker-checker approval, hard duplicate block, and audit transitions remain server enforced. No payment is initiated.

The risk score is a review priority, not a calibrated fraud probability. A duplicate paid invoice scores 100 and is blocked. A changed account adds 75. A supplier with no paid history adds 45. Amount deviation is assessed only after at least three prior amounts using the historical median. Signals can combine, capped at 100. Bank account history is based on previously recorded paid supplier payments; this does not prove bank ownership. The browser displays the old and new destinations masked, historical count, signal evidence, recommended review step, and assessment history. Uploaded invoices and future Jinius sandbox records use the same risk engine; no live Jinius endpoint or payment capability is implemented.

## API

`POST /api/v1/invoice-intakes` accepts multipart `file` and optional `Idempotency-Key`; `GET /api/v1/invoice-intakes/{id}` reads the draft; `POST /extract` retries extraction; `PATCH /api/v1/invoice-intakes/{id}` confirms corrected fields and supplier; `POST /analyze` creates the policy assessment; `GET /document` downloads the private original. `GET /api/v1/invoices/{id}/assessments` and `GET /api/v1/invoices/{id}/assessments/{assessment_id}` expose immutable policy snapshots. Standard invoice, document, and audit endpoints expose the persisted result. Processing errors return explicit HTTP errors or a retryable intake state; the frontend does not claim success after a failed write.

## Verification

Run `py -m pytest tests -q` and, in `frontend`, `npm run test`, `npm run typecheck`, `npm run lint`, and `npm run build`. The pull-request workflow starts a disposable local Supabase stack, applies migrations, runs pgTAP RLS tests, and executes the PostgreSQL API integration scenario with synthetic PDFs. That scenario covers the 14-payment changed-account case, idempotency, tenant isolation, persisted document and assessment, approval bypass, audit, and unknown supplier. Other synthetic unit cases cover duplicate invoices, amount deviation, missing IBAN, unreadable PDF, and malicious document instructions. Live model calls require a separately configured development key and are not made by the automated tests.

The current implementation uses a strict local label parser for text PDFs and a vision model for synthetic scans/images when enabled. It does not perform OCR without the model, calibrate a fraud probability, verify IBAN ownership, connect to real Jinius, or initiate payments. Production use requires a retention policy, provider contract, operational monitoring, and security review.
