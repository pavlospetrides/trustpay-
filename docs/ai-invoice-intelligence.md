# Universal invoice reader

This feature runs in `TRUSTPAY_BACKEND=postgres` with Supabase Auth, the private `invoice-documents` bucket, and migration `20261123000300_invoice_intake.sql`. SQLite remains the separate synthetic demo. The browser calls the Next.js server with the user's Supabase access token and selected organization. All intake queries scope by that organization. The server encrypts extracted fields, including the full IBAN, with the existing AES-GCM key and keeps documents in private Storage. API responses show the full proposed IBAN only to an authenticated organization member during review; persisted risk results show masked account identifiers.

## Configuration

An opt-in OCR candidate is available with `TRUSTPAY_INVOICE_READER=ocr`; leaving it unset uses the existing Vision reader. OCR uses PDF.js per-page native text and locally installed English/Greek Tesseract.js data. It sends text and word boxes to OpenAI for the same structured analysis, without sending document bytes in that path. Weak OCR can fall back to Vision only when the external-document opt-in below is enabled. The candidate's [measured limits and rollout decision](invoice-ocr-evaluation.md) are recorded separately.

Use Node.js 24.11.1 through 24.x and run `npm ci` in `frontend`. Apply the additive WEBP migration to an explicitly designated development project before uploading WEBP originals there; this branch does not apply it to any hosted or production database. Configure the existing PostgreSQL, Supabase, and IBAN key variables in `.env.local`. For **synthetic development invoices only**, set `OPENAI_API_KEY`, `TRUSTPAY_ENVIRONMENT=development`, and `TRUSTPAY_AI_EXTERNAL_DOCUMENTS=development` to enable the multimodal reader, then restart the server. A key alone does not authorize external document transfer. `TRUSTPAY_AI_MODEL` defaults to `gpt-5.4-mini`, which [supports image input and structured outputs](https://developers.openai.com/api/docs/models/gpt-5.4-mini). The provider sends PDF page images at high detail, has a 90-second timeout, one SDK retry, strict Zod output, `store: false`, and a process-local concurrency limit of two requests with a queue of eight. Keep the API key on the backend. With external processing disabled, text PDFs use a local best-effort parser; scanned PDFs and images enter an explicit provider-unavailable state and can be entered manually. Retry becomes available only when the provider is configured, so it does not repeat the same local parser. Do not enable external processing for customer documents without authorization and data-processing controls.

## Workflow

An analyst, owner, or admin uploads a PDF, PNG, JPEG or WEBP of at most 10 MB. The server validates signatures and decodes images with a 20-million-pixel cap, accepts up to ten PDF pages, limits each uploader to 20 intakes per hour and each intake to two retries, and stores the exact original privately. The multimodal reader receives the complete document and bounded embedded PDF text. It returns document classification, detected languages, source page and supporting text, supplier/customer/banking fields, totals, VAT and line items. TypeScript independently checks IBAN, dates, decimal amounts, gross/balance and line calculations. If embedded PDF text contains a valid IBAN omitted by the model's account list, the payable IBAN is cleared and the reviewer sees a warning. Gross-total validation accepts invoices that report net amounts before or after a separately printed discount. The review screen shows evidence and allows correction; original model values and reviewed values remain separate in tenant-scoped ciphertext. Audit records corrected field names without sensitive values. Identical document hashes can reuse a prior model result inside the same organization process. AI usage tokens are stored with the encrypted draft; optional `TRUSTPAY_AI_INPUT_USD_PER_M` and `TRUSTPAY_AI_OUTPUT_USD_PER_M` configure an estimated cost display. A reviewed invoice is passed to the existing deterministic TypeScript policy engine. Its immutable assessment and signals are stored in PostgreSQL. An optional model summary receives only masked account identifiers, score, historical payment count, level, and signal codes; it cannot change the policy decision. Existing verification, maker-checker approval, hard duplicate block, and audit transitions remain server enforced. No payment is initiated.

If the model flags multiple invoices, split the original file and upload each invoice separately. For a false positive, a reviewer must inspect every page, explicitly confirm that there is one invoice and enter a reason of at least 20 characters; the original classification, confirmation and reason remain in the encrypted intake and an override audit event is written. Changing any other document type to a payable invoice also requires a documented override. A missing IBAN may be saved as a reviewed draft, but the server refuses risk analysis until a valid destination IBAN is confirmed. Gross total and outstanding balance can be corrected separately; the payable amount must match the appropriate reviewed value.

The risk score is a review priority, not a calibrated fraud probability. A duplicate paid invoice scores 100 and is blocked. A changed account adds 75. A supplier with no paid history adds 45. Amount deviation is assessed only after at least three prior amounts using the historical median. Signals can combine, capped at 100. Bank account history is based on previously recorded paid supplier payments; this does not prove bank ownership. The browser displays the old and new destinations masked, historical count, signal evidence, recommended review step, and assessment history. Uploaded invoices and future Jinius sandbox records use the same risk engine; no live Jinius endpoint or payment capability is implemented.

## API

`POST /api/v1/invoice-intakes` accepts multipart `file` and optional `Idempotency-Key`; `GET /api/v1/invoice-intakes/{id}` reads the draft; `POST /extract` retries extraction; `PATCH /api/v1/invoice-intakes/{id}` confirms corrected fields and supplier; `POST /analyze` creates the policy assessment; `GET /document` downloads the private original. `GET /api/v1/invoices/{id}/assessments` and `GET /api/v1/invoices/{id}/assessments/{assessment_id}` expose immutable policy snapshots. Standard invoice, document, and audit endpoints expose the persisted result. Processing errors return explicit HTTP errors or a retryable intake state; the frontend does not claim success after a failed write.

## Verification

In `frontend`, run `npm run test`, `npm run typecheck`, `npm run lint`, and `npm run build`. The pull-request workflow starts a disposable local Supabase stack, applies migrations, runs pgTAP RLS tests, and runs `src/lib/server/testing/disposable-db.test.ts`, the PostgreSQL API integration scenarios with synthetic PDFs. That scenario covers the 14-payment changed-account case, idempotency, tenant isolation, persisted document and assessment, approval bypass, audit, and unknown supplier. Other synthetic unit cases cover duplicate invoices, amount deviation, missing IBAN, unreadable PDF, and malicious document instructions. Live model calls require a separately configured development key and are not made by the automated tests.

The local parser is only a fallback when document sharing is disabled or the provider fails. It marks missing critical fields as a partial or failed extraction, and the review screen names the actual method and highlights missing fields. It does not OCR scans or provide multilingual layout understanding. The model can misread low-quality, handwritten, or ambiguous documents; every extracted field requires human review. Credit notes, proformas, unrelated documents and uploads containing multiple invoices cannot enter the payable assessment workflow as one invoice. The existing assessment engine supports EUR amounts only. The reader does not calibrate fraud probabilities, verify bank account ownership, connect to a live Jinius API or initiate payments. Production use requires authorized document sharing, a retention policy, provider contract, operational monitoring and security review.
